Parsar separates coordination from execution. The server stores the team's context and durable records; a Runtime executes the Agent and reports events back. The values below are the values enforced by the current server and database schema.

## Workspace objects

| Object | Responsibility |
| --- | --- |
| Workspace | Isolates members, Agents, conversations, settings, credentials, and history. |
| Agent | Reusable identity and execution configuration: connector, model, instructions, capabilities, visibility, and Runtime binding. |
| Runtime | Concrete execution environment such as a paired `parsar-daemon`, local sandbox, or external Agent endpoint. |
| Conversation | Durable context for web, instant-messaging, or API interaction. |
| Agent Run | One concrete execution triggered from a conversation or another supported entry point. |
| Capability | A reusable Skill, MCP server, Plugin, System Prompt, or Bundle attached to an Agent. |
| Connector | The protocol boundary used to deliver work. Agent connectors are `agent_daemon` and `http`; Feishu, Slack, Discord, and Teams are workspace messaging connectors. |

## The important distinction

An Agent is not a daemon process. It is configuration and identity. A Runtime is where execution happens. A Run is one execution record. One Runtime can serve multiple Agents; one Agent can produce many Runs over time.

## Parsar's work model

Parsar currently uses Conversations and Agent Runs as its primary work records. A Conversation keeps the human-facing context; a Run records one attempt to execute that context. Scheduled Tasks provide recurring triggers. This is different from a separate first-class project or issue tracker: a Conversation does not have project fields, issue numbers, or a project resource checkout.

Workspace, Agent, Runtime, Capability, and Scheduled Task records are the stable objects to reference in integrations and automation.

## Enumerations you will see in the API

### Agent kind and connector

An Agent's `config.agent_kind` selects the command-line engine discovered by the daemon:

| Agent kind | Streaming | Permission requests | Resume | Usage reporting |
| --- | --- | --- | --- | --- |
| `claude_code` | yes | yes | yes | yes |
| `codex` | yes | yes | yes | yes |
| `opencode` | yes | no | no | yes |
| `pi` | yes | no (runs with `--no-approve`) | yes | yes |

The connector type is `agent_daemon` for a paired or managed daemon and `http` for an external HTTP Agent endpoint. Availability and version are discovered when a daemon connects; they are not hard-coded in the browser.

### Visibility, membership, and runtime states

Agent visibility has exactly three values:

| Value | Who can open the Agent |
| --- | --- |
| `workspace` | Active members of the owning Workspace |
| `tenant` | Any registered Parsar user; workspace members are included |
| `public` | Registered users and unauthenticated guests (guests are prompted to register) |

Workspace visibility is a separate field with `private` and `public`. Membership status is `pending`, `active`, or `rejected`; only `active` members participate in workspace access checks. Runtime liveness is `pending_pairing`, `offline`, `online`, or `error`.

## Run lifecycle

Runs use exactly six statuses: `queued` (waiting to start), `running` (actively executing), `completed` (normal success), `failed` (execution error), `cancelled` (user-initiated cancellation), and `interrupted` (system interruption or runtime failure). The last four are terminal. A completed Run does not automatically mean the Conversation is finished; the Conversation keeps its messages and can trigger another Run.

Do not confuse Run status with an Agent Interaction. Approval and choice interactions have their own lifecycle: `pending`, `resolving`, `approved`, `denied`, `answered`, `cancelled`, or `expired`.

## Human interaction

Permission requests and user-choice prompts are durable interactions. They can be resolved in the Web approval inbox or in a conversation surface, and the same resolution service records the terminal decision.
