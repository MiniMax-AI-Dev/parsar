title: Parsar 的工作方式
description: 从发送消息到查看结果，了解服务端和执行设备各自负责什么。

Parsar 保存和协调工作，执行设备上的编程 CLI 完成任务。浏览器、Parsar 服务、执行设备和模型服务需要各自可用。

## 一条消息如何执行

1. 你在对话中发送请求，Parsar 根据对话绑定或消息提及找到 Agent。
2. 服务端检查访问权限，保存消息并创建 Run。
3. Agent Daemon 连接器将请求交给所选 Runtime；daemon 启动对应引擎，传入模型、指令、能力和工作目录。
4. 引擎调用模型及工具，把回复、工具事件和交互请求返回 Parsar。
5. 你在对话中查看回复，在收件箱处理请求；执行结束后 Run 记录最终状态。

已有 HTTP Agent 通过外部 HTTP 服务执行，不经过本地编程 CLI。当前新建 Agent 使用本地设备或云端隔离，配置步骤见[创建和配置 Agent](/zh/create-agent)。

## 各部分负责什么

| 部分 | 职责 |
| --- | --- |
| 浏览器 | 发送消息、展示进度、处理请求和管理配置。 |
| Parsar 服务 | 认证与授权、保存资源、调度运行、记录历史及审计。 |
| 执行设备上的 daemon | 发现编程 CLI、启动进程、准备工作目录、回传执行事件。 |
| 编程 CLI 与模型服务 | 生成回答、调用工具、报告结果与用量。 |

本地设备主动连接服务端。服务端不会通过浏览器访问你的本地目录；Agent 只能使用执行设备可访问的文件和网络。

## 在哪里查看结果

- **对话**：消息、回复和当前交互请求。
- **运行 → 对应记录**：状态、Steps（步骤）、Artifacts（产物）和 Audit（审计），以及已记录的执行环境信息。
- **设置 → 用量**：引擎已上报的 Token 和费用数据。

产物和用量依赖执行端实际提交。没有产物记录时显示空状态；没有上报用量不表示模型没有产生费用。

## 执行没有进展时

Run 的排队中表示已创建但未开始执行，运行中表示执行器已接管但尚未结束。这些状态不代表模型已经开始输出。

检查 Run 的最新事件、**收件箱**待处理请求和**执行层**设备状态。设备离线、缺少 CLI、模型拒绝请求或缺少凭据，都需要按错误信息修复；设备重新上线不会自动重试已失败的 Run。

服务端保存已接收的消息和运行记录，刷新浏览器不会清除这些历史。恢复设备连接与重新发起运行是不同操作，排查步骤见[故障排查](/zh/troubleshooting)。
