An Agent Run is one execution record. The Conversation timeline shows the user-facing result; the Run detail view shows the operational evidence behind it.

## Run states

| State | Meaning |
| --- | --- |
| `queued` | The server accepted the request and is waiting for the bound Runtime. |
| `running` | The Runtime has started the Agent process. |
| `completed` | The Agent finished and the server persisted the result. |
| `failed` | Execution ended with an error or provider failure. |
| `cancelled` | A user-initiated cancellation ended the Run. |
| `interrupted` | A system interrupt or Runtime failure stopped execution before a normal terminal result. |

## Read a Run

Open **Runs** and select a record. Depending on the Run, the detail view can include:

- request and requester;
- Agent and connector;
- Runtime snapshot and heartbeat information;
- status events and streamed tool calls;
- output message and transcript;
- artifacts such as screenshots or tool output;
- model usage and token counts;
- error summary and user-facing reason.

## Approvals and user choices

Some providers pause for permission or ask the user to choose an option. Parsar persists these as Interactions with a bounded lifetime. Resolve them in **Approvals** or in the active Conversation. The decision is applied only after the runtime acknowledges it.

Interaction status is separate from Run status: `pending`, `resolving`, `approved`, `denied`, `answered`, `cancelled`, and `expired`. Never paste secrets into a non-secret answer field. Secret answers are redacted from durable interaction responses, audit events, logs, API reads, and rendered receipts.

## When a Run is queued or failed

Start with the Runtime snapshot, then check the Agent's connector, model credentials, required Capabilities, and daemon logs. The [Troubleshooting](/troubleshooting) page follows the same server → daemon → provider order.
