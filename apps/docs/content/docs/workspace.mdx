title: Workspaces
description: Understand the workspace boundary, membership, and lifecycle in Parsar.

A workspace is Parsar's tenant boundary. Agents, conversations, runs, runtimes, capabilities, credentials, scheduled tasks, and audit records are scoped to a workspace.

## What belongs to a workspace

| Area | Workspace-scoped data |
| --- | --- |
| Team | Members, roles, invitations, and join requests |
| Agents | Agent identity, connector, visibility, capabilities, and runtime binding |
| Execution | Conversations, runs, approvals, artifacts, and usage records |
| Operations | Runtimes, daemon pairings, scheduled tasks, and audit events |
| Configuration | Models, credentials, secrets, connectors, and imported capabilities |

The workspace boundary is also the first permission check on API requests. Selecting another workspace changes the active scope; it does not move or copy data.

## Create a workspace

1. Sign in to Parsar.
2. If your account has no memberships, complete the onboarding form to create the first workspace.
3. Otherwise open the workspace switcher and choose **Create workspace**.
4. Enter a display name and choose `private` or `public` visibility.

The creator becomes the initial `owner`. A private workspace is invitation-only. A public workspace can appear in discovery and accept join requests, subject to the server's registration policy.

## Switch, join, or leave

The workspace switcher lists workspaces in which your account has an active membership. A public workspace can be discovered and joined through a request flow; an owner or admin approves or rejects pending requests.

Leaving a workspace removes your active membership. Before leaving, move ownership of any runtime or agent configuration that the team still needs. The final owner cannot leave until another member is promoted.

## Update or archive

Owners and admins can update workspace metadata. Archiving is a soft lifecycle operation: it removes the workspace from normal active use while preserving server-side records according to the retention policy. It is different from deleting a resource in the UI; always verify the current confirmation dialog before destructive actions.

## Permission boundaries

Workspace membership is necessary but not sufficient to run an Agent. The Agent's own visibility and Access policy, the selected Runtime, and the required credentials are checked independently. See [Members and roles](/members-roles), [Create and configure an Agent](/create-agent), and [Capabilities](/capabilities).
