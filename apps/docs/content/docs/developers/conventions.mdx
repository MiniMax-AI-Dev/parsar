---
title: Repository conventions
description: Package boundaries, generated contracts, and quality rules for Parsar changes.
---

Parsar follows a “grep before you write” rule: reuse an existing formatter, parser, error mapper, or shared frontend helper before adding a near-duplicate. Shared Web formatting and labels belong in `apps/web/src/lib/` rather than in individual pages.

## Size and ownership

Go files over roughly 500 lines and React components over roughly 400 lines are signals to extract a focused module. `server/internal/dev/routes.go`, `server/internal/store/store.go`, and `apps/web/src/pages/admin/AgentsPage.tsx` are already oversized; do not add more weight to them when touching adjacent behavior.

## Generated contracts

- Handler/API changes: add swaggo annotations, run `make openapi`, and review `docs/openapi/openapi.yaml`.
- Database query changes: run `make sqlc-generate` and review the generated sqlc files.
- Every change: run `make check` before reporting completion.

Prefer explicit error mapping and one response helper per API surface. Keep docs examples aligned with actual flag names, environment variables, enum values, and file paths.

See [`AGENTS.md`](https://github.com/AllureCurtain/parsar/blob/main/AGENTS.md) for the short agent index and [`CONTRIBUTING.md`](https://github.com/AllureCurtain/parsar/blob/main/CONTRIBUTING.md) for the canonical long form.
